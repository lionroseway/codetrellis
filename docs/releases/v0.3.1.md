CodeTrellis 0.3.1 makes Python rules see every import. A rule that looked clean may have been missing most of what breaks it, so read the first section if you use a baseline.

## ⚠️ Before you start

- **Using `.codetrellis/rules/baseline.yaml` with Python? Do this before you move CI to 0.3.1.** 0.3.0 read only a Python file's top-level imports. 0.3.1 also sees those inside a function, a `try:`, an `if` or under `if TYPE_CHECKING:`, so a baseline written by 0.3.0 can list too few, and every check then fails with `… and its baseline does not list it`, on any change. `codetrellis rules baseline` will not add them, because a baseline only shrinks.
  1. While CI is still on 0.3.0, remove the affected rules from `baseline.yaml` in a pull request. Its check passes there.
  2. Once that has merged, run `codetrellis rules baseline` on 0.3.1 and commit the result, then move CI to 0.3.1.

  If CI has already moved, that first pull request fails its own check and has to be merged over it.
- **No baseline?** Nothing to do. The check judges only what a change adds, so existing code does not start failing. The Rules view will show the breaches it was missing.

## 📏 Rules

- **Python package rules no longer under-report.** A rule now finds an import wherever in the file it is. On one real repository, a rule that recorded 30 files now finds all 57. Rules about who may import a file or a named export see these imports too, and they appear as edges on the graph.
- **Write a Python package the way pip does or the way the code does.** `pypi:langchain-ollama` and `pypi:langchain_ollama` are now one package, and case does not matter. Before, the hyphenated spelling matched nothing and said nothing. A distribution whose module has another name is still named by its module: `pypi:yaml` for PyYAML.
- **Your machine and CI now agree straight after an upgrade.** The first scan on a new version parses every file again, so a machine that had already scanned no longer keeps the old answer for files that have not changed.
