# 0.3.0 — the release plan, for the release machine

Phase 33 (rules and clarity) ships as **0.3.0**, the owner's decision: the CLI
and the pipeline checks are a major step. This is the brief for a Claude Code
session on the release Mac. Follow it top to bottom; it adds what 0.3.0 needs
to [`RUNBOOK.md`](RUNBOOK.md), which was written for 0.1.18.

## Read first

1. `CLAUDE.md`: the security rules, "Releasing", and "A packaged build is
   the only thing that proves this".
2. `docs/releases/RUNBOOK.md`: the steps. Where it says 0.1.18 read **0.3.0**,
   and where it says 0.1.17 (the upgrade path) read **0.2.0**.
3. `docs/phase-33/LOG.md`: what the phase built and where it stands.
4. `docs/claude/cli.md`: "From the desktop app", "The npm package",
   "Publishing it".
5. `.claude/skills/codetrellis-release-notes/SKILL.md`, for the notes.

## The rules

- **Nothing is public until RUNBOOK step 6**, and step 6 runs only once steps
  3 to 5 have passed on the build step 2 made.
- **Stop and ask the owner** before:
  - merging anything into `main`;
  - RUNBOOK step 6 (publishing);
  - submitting the phone build.

  Say what you checked when you ask.
- **The suite was green at the start, so any failure is ours.** Never skip,
  disable or quarantine a test. Fix it on a branch with a test, PR, merge on
  green.
- **Node 26 for everything** (`node -v`). **`npm ci` before packaging**,
  never a reused `node_modules`.
- **No secrets in the tree, issues or PRs.** The source repo is public.
- **Commit trailers** as CLAUDE.md and the repo's history do. No model names
  in commits or PRs.

## If something fails

Stop before step 5. Nothing is public until then.

- Write what happened in an issue, without security details.
- Fix it on a branch with a test, PR it into `main` (or `feat/phase-33` before
  step 3), then start again from the step that failed.
- Diagnose a packaging fault only from a clean `npm ci`.
